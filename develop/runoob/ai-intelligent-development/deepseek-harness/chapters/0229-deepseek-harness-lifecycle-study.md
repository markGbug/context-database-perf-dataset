## 本章内容

在前面的章节中，我们已经学习了如何注册事件监听器、工具，以及使用 ctx.effect() 管理资源。

但这些注册什么时候开始生效？插件卸载时，事件监听器和工具又是如何被清理的？

DeepSeek Harness 使用 Cordis 插件模型管理这些过程。每个插件实例都有一个对应的 Fiber，负责跟踪插件状态、依赖关系和需要清理的资源。

本章节介绍 Fiber 生命周期、依赖驱动加载、自动清理机制，以及插件的手动卸载和热替换。


## Fiber 是什么？

Fiber 是 Cordis 中表示一个插件运行实例的对象。

当插件被加载时，框架会创建对应的 Fiber，用于管理插件的生命周期。

一个 Fiber 主要负责以下工作：

- 记录插件当前的生命周期状态。
- 保存经过校验的插件配置。
- 跟踪插件需要的服务依赖。
- 管理插件注册的事件、工具和其他资源。
- 在插件卸载时执行清理操作。

可以通过 ctx.fiber 获取当前插件所属的 Fiber。

例如：

```javascript
export function apply(ctx: Context) {
  const fiber = ctx.fiber

  console.log(fiber.state)
}
```

其中，fiber.state 表示当前生命周期状态。

注意：一个插件模块和一个 Fiber 并不完全相同。同一个插件可以被应用到不同上下文中，每个加载实例可以拥有独立的 Fiber。


## Fiber 状态机

Fiber 使用状态机管理插件从加载到卸载的过程。

一个正常加载并最终卸载的插件，通常经历以下状态：

```text
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
```

如果插件加载过程中发生错误，则可能进入 FAILED 状态。

各状态的含义如下：

例如，一个正常加载的插件会先进入 LOADING，执行 apply() 中的初始化操作，成功后进入 ACTIVE。

当插件需要卸载时，会进入 UNLOADING，执行相应的资源清理，完成后进入 DISPOSED。

如果初始化失败，插件可能进入 FAILED。具体错误需要通过日志或框架提供的诊断接口检查，不能将所有加载失败都理解为缺少依赖。


## 依赖驱动的加载

Cordis 支持根据服务依赖决定插件的加载时机。

插件可以通过 inject 声明自己依赖哪些服务。

例如，一个插件需要使用工具注册服务 tools 和大语言模型服务 llm。


## 实例

当 tools 或 llm 尚未就绪时，插件会等待依赖，不会立即执行 apply()。

等到必需服务全部就绪后，Cordis 才会加载插件。

这样开发者就不需要手动编写复杂的初始化顺序。


### 依赖消失时会怎样？

Cordis 的依赖机制不仅影响插件首次加载，也会影响已经运行的插件。

例如：

- 插件依赖 tools 和 llm 服务。
- 两个服务都就绪后，插件进入运行状态。
- 运行过程中，llm 服务被卸载或替换。
- Cordis 自动卸载依赖该服务的插件，并清理旧注册。
- 当所需服务重新就绪后，插件可以重新加载。

这意味着，依赖服务发生变化时，框架可以自动管理相关插件的卸载与重新初始化。

需要注意，自动重新加载不等于恢复旧插件中的所有运行时数据。如果插件需要在重新加载后保留状态，应通过适当的外部存储或状态管理机制实现。

### 异步清理需要注意什么？

如果处置器包含异步操作，框架会等待相关异步清理任务完成，但多个异步处置器不保证按照注册顺序逐个执行完毕。

例如，需要先关闭会话，再关闭数据库连接时，不应将两个步骤拆分为相互独立的异步处置器。

## 热替换（HMR）与生命周期

HMR（Hot Module Replacement，热模块替换）允许开发者在修改插件代码后更新运行中的插件，而不必每次都手动重启整个应用。

在 DeepSeek Harness 中，如果已经通过 cordis.yml 加载并配置 @deepseek-ai/dsh-hmr，修改受监控的插件源码后，可以触发热替换。

一次典型的热替换包含以下步骤：

- 检测插件源文件发生变化。
- 卸载旧插件实例。
- 移除旧实例注册的事件、工具等资源。
- 加载更新后的插件代码。
- 重新执行插件的初始化逻辑。

例如，一个插件注册了工具 my_tool，然后开发者修改了该工具的实现。

如果热替换成功，框架会先清理旧插件的工具注册，再加载新版工具，避免由于旧注册没有释放而产生重复注册问题。

但需要注意，热替换不代表插件内部状态会被自动持久化。对于必须保留的数据，应使用独立的状态存储或恢复机制。

## 常见问题


### 1、插件没有执行 apply()？

首先检查是否声明了 inject，以及对应的必需服务是否已经就绪。

如果依赖尚未就绪，插件可能停留在 PENDING 状态。

如果依赖已经满足，则应继续检查配置校验和插件初始化过程中是否发生异常。


### 2、插件卸载后定时器还在运行？

如果定时器是直接通过 setInterval() 创建的，而没有注册对应的清理函数，Cordis 可能无法自动管理它。

应将定时器创建过程放入 ctx.effect()，并返回调用 clearInterval() 的处置器。
